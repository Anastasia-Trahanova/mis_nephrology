# МИС Нефролога

Веб-приложение для организации амбулаторного приёма нефролога: ведения пациентов, медицинских приёмов, лабораторных и инструментальных исследований, расчёта нефрологических показателей, расписания врачей, регистра ХБП и формирования заключений в Word.

> Проект находится в разработке и не является зарегистрированным медицинским изделием. Результаты расчётов требуют врачебной интерпретации.

## Возможности

- авторизация сотрудников с ролями врача и администратора;
- защищённые сессии с контролем бездействия;
- проверка допустимого имени хоста через `TrustedHostMiddleware`;
- поиск и регистрация пациентов;
- первичные и повторные приёмы;
- подстановка данных предыдущего приёма без создания дублей диагнозов;
- карточка пациента с историей приёмов;
- жалобы, анамнез, осмотр, диагнозы МКБ-10, назначения и рекомендации;
- динамические таблицы ОАК, биохимии, ОАМ и альбуминурии;
- хранение данных УЗИ и других исследований;
- расчёт ИМТ, CKD-EPI 2021, Cockcroft–Gault, стадии ХБП, ACR и категории альбуминурии A1/A2/A3;
- оценка риска прогрессирования ХБП по KDIGO;
- расписание врачей;
- отметки статуса записи и переход из расписания к пациенту или медицинскому приёму;
- регистр пациентов с ХБП;
- экспорт выбранного приёма в DOCX;
- журнал действий пользователей для администратора;
- горячие клавиши и встроенная справка по ним.

## Установка

### 1. Создать виртуальное окружение

Windows CMD:

```bat
python -m venv venv
venv\Scripts\activate
```

### 2. Установить зависимости

```bat
python -m pip install --upgrade pip
pip install -r requirements.txt
pip install -r requirements-dev.txt
```

Для браузерных тестов дополнительно:

```bat
pip install playwright
python -m playwright install chromium
```

### 3. Настроить окружение

Скопируйте шаблон:

```bat
copy .env.example .env
```

Заполните `.env`:

```env
APP_ENV=dev
ALLOWED_HOSTS=localhost,127.0.0.1,testserver

DB_HOST=localhost
DB_PORT=5432
DB_NAME=mis_for_registrations
DB_USER=postgres
DB_PASSWORD=change_me

DB_POOL_MIN_CONN=1
DB_POOL_MAX_CONN=10

SESSION_SECRET_KEY=change_me_dev_secret
SESSION_COOKIE_NAME=mis_nephrology_session
SESSION_COOKIE_MAX_AGE_SECONDS=604800
SESSION_IDLE_TIMEOUT_SECONDS=3600
SESSION_KEEPALIVE_INTERVAL_SECONDS=180
SESSION_HTTPS_ONLY=false
```

Файл `.env` содержит секреты и не должен попадать в Git.

## База данных

Проект использует PostgreSQL.

Актуальная версия базы создаётся из итоговых SQL-файлов в папке `database`. Исторические миграции ранних версий не применяются при создании новой базы.

### Структура файлов базы

```text
database/
├── 01 создание таблиц.sql
├── 02 настройка связей ключей и ограничений.sql
├── 03 заполнение справочников МКБ и лекарств.sql
├── 04 справочник больницы и пользователи.sql
├── 05 заполнение тестовыми данными.sql
├── 06 проверка структуры и справочников.sql
├── 07 проверка тестовых данных.sql
└── 08 проверка архивного расширения.sql
```

Назначение файлов:

1. `01 создание таблиц.sql` — создаёт итоговые таблицы приложения.
2. `02 настройка связей ключей и ограничений.sql` — создаёт первичные и внешние ключи, ограничения и индексы.
3. `03 заполнение справочников МКБ и лекарств.sql` — загружает постоянные медицинские справочники.
4. `04 справочник больницы и пользователи.sql` — загружает врачей, подразделения и установочные учётные записи организации.
5. `05 заполнение тестовыми данными.sql` — добавляет демонстрационных пациентов, приёмы и связанные медицинские данные.
6. `06 проверка структуры и справочников.sql` — проверяет итоговую структуру и постоянные справочники.
7. `07 проверка тестовых данных.sql` — проверяет демонстрационное наполнение.
8. `08 проверка архивного расширения.sql` — проверяет поля и ограничения, необходимые для архивного импорта.

### Важное предупреждение

Команда с параметром `--yes` удаляет базу с указанным именем и создаёт её заново.

Не указывайте имя базы, содержащей необходимые реальные данные.

### 1. Контрольное создание базы с тестовыми данными

Для проверки структуры создайте отдельную временную базу:

2. создаёт новую PostgreSQL-базу;
3. создаёт таблицы;
4. создаёт связи, ограничения и индексы;
5. загружает МКБ, лекарства и справочник больницы;
6. проверяет структуру и справочники;
7. загружает тестовые данные;
8. проверяет тестовое наполнение.

После успешного выполнения должны появиться сообщения:


## Авторизация и доступы

В текущей версии вход предназначен только для сотрудников медицинской организации:

- врач после входа видит общую базу пациентов;
- врач может открыть карточку любого пациента и добавить ему новый приём;
- администратор использует административные разделы и журнал действий;
- личный кабинет пациента и вход пациента в систему пока не реализованы; поле роли пациента в базе зарезервировано для будущего развития.

Публично доступны только страница входа и статические файлы, необходимые для её отображения. Остальные маршруты требуют активной сессии через зависимости FastAPI. Сессия завершается после установленного периода бездействия.

## Важные соглашения

- Стадии ХБП хранятся с русской буквой `С`: `С1`, `С2`, `С3а`, `С3б`, `С4`, `С5`.
- Будущая запись в расписании не должна считаться состоявшимся медицинским приёмом.
- Миграции нельзя удалять после применения к используемым базам.
- В Git нельзя помещать `.env`, дампы БД, журналы, временные архивы и реальные персональные медицинские данные.

## Безопасность

Приложение использует несколько независимых уровней защиты:

- `TrustedHostMiddleware` принимает запросы только для хостов из `ALLOWED_HOSTS`;
- публичными остаются только `/login` и статические ресурсы страницы входа;
- внутренние маршруты требуют активной подписанной сессии через зависимости FastAPI;
- после периода бездействия сессия становится недействительной;
- пароли хранятся только в виде хеша PBKDF2-SHA256;
- переход после входа разрешён только на локальный путь приложения.

Для локальной разработки используются:

```env
ALLOWED_HOSTS=localhost,127.0.0.1,testserver
SESSION_HTTPS_ONLY=false
```

Для production необходимо:

- перечислить в `ALLOWED_HOSTS` только реальные доменные имена сервиса без `http://`, `https://` и пути;
- не использовать `ALLOWED_HOSTS=*`;
- использовать длинный случайный `SESSION_SECRET_KEY`;
- включить HTTPS и установить `SESSION_HTTPS_ONLY=true`;
- создать отдельную учётную запись для каждого сотрудника;
- регулярно выполнять резервное копирование PostgreSQL;
- не использовать демонстрационные данные и пароли.
